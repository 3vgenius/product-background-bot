# product-background-bot

Telegram-бот, который вырезает товар с фотографии и ставит его на выбранный фон.
Фоны хранятся в общей библиотеке, результат — JPEG выбранного размера.

Работает **бесплатно**: приём сообщений на Render Free, тяжёлое вырезание — на
GitHub Actions.

## Как это устроено

```
 Пользователь
      │  фото товара
      ▼
 Render Free Web Service  ── workflow_dispatch ──►  GitHub Actions runner
 app.py (Flask, 512 MB)      (только file_id)        2 vCPU / 7-8 GB, бесплатно
      │                                                    │
      │                                          rembg: вырезать товар
      │                                          наложить фон, JPEG
      │                                                    │
      ◄──────────── sendDocument ──────────────────────────┘
                          (результат приходит прямо в чат)

 Хранилище = этот репозиторий
   backgrounds/*.jpg + backgrounds.json   общая библиотека фонов
   settings.json                          выбор фона и настройки каждого юзера
```

Ключевые решения:

- **Render не обрабатывает картинки.** Из апдейта Telegram берётся только
  `file_id` (короткая строка), а сам файл скачивает уже раннер через Bot API.
  Поэтому хватает бесплатных 512 МБ.
- **Библиотека фонов живёт в репозитории.** Ни SQLite, ни persistent disk — на
  Render нет бесплатного background worker, а платный диск дороже самого
  compute. Запись идёт через GitHub Contents API, чтение на Render — тоже
  через API (чекаут Render заморожен на момент деплоя, читать из него нельзя;
  на раннере Actions, наоборот, чекаут свежий, и там читается локально —
  переключатель `STORE_PREFER_LOCAL`, по умолчанию выставляется сам).
  Коммиты бота помечены `[skip render]`, чтобы каждое нажатие кнопки не
  пересобирало сервис.
- **GitHub-hosted раннер в ~14 раз больше по памяти, чем Render Starter**
  (7-8 ГБ против 512 МБ), и он бесплатный в пределах 2000 минут в месяц на
  приватной репе. Именно поэтому доступен BiRefNet.

## Команды бота

| Команда | Что делает |
|---|---|
| `/start`, `/help` | справка |
| `/bg` | добавить фон в общую библиотеку: отправьте `/bg` (можно с именем: `/bg Мрамор`), затем картинку следующим сообщением. Работает и одним сообщением — картинка с подписью `/bg` |
| `/backgrounds` | посмотреть библиотеку и выбрать фон себе. Кнопка 🗑 удаляет фон у всех — после подтверждения; у тех, кто его выбрал, выбор сбрасывается. Кнопка 🧹 убирает с фона лишние объекты (см. ниже) |
| 🧹 Убрать объекты с фона | кнопка после `/bg` и в `/backgrounds`. Бот находит на фоне объекты (той же моделью, что вырезает товары), закрашивает их под окружение и сохраняет очищенную копию рядом с оригиналом. Товары дальше ставятся на очищенную версию; кнопка «↩️ Вернуть оригинал» откатывает всё обратно |
| `/once` | разовый фон: отправьте `/once`, затем картинку (или картинку с подписью `/once`). Сработает на следующее фото товара, в библиотеку не попадёт. Сбрасывается только после того, как результат реально пришёл в чат — если обработка не запустилась или упала, просто пришлите фото товара ещё раз |
| `/settings` | качество вырезания (⚡ Быстро / 💎 Качество) и размер результата |
| `/cancel` | сбросить незавершённый сценарий и разовый фон |
| фото товара | вырезать и поставить на выбранный фон |

Для лучшего качества исходник лучше отправлять **файлом**, а не фото Telegram —
Telegram пережимает фотографии.

## Настройка

### 1. GitHub

В репозитории: **Settings → Secrets and variables → Actions**.

Secrets:

| Имя | Значение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен от [@BotFather](https://t.me/BotFather) |

Variables (вкладка **Variables**):

| Имя | Значение |
|---|---|
| `RENDER_URL` | полный URL сервиса Render, например `https://product-background-bot-a1b2.onrender.com` |

Отдельный **classic PAT** понадобится самому Render. Создайте на
github.com/settings/tokens с областями **`repo`** и **`workflow`**:
`repo` пишет фоны и настройки через Contents API, `workflow` запускает
`process.yml`.

### 2. Render

1. dashboard.render.com → **New → Web Service** → подключить этот репозиторий.
   Можно использовать `render.yaml` (**New → Blueprint**), тогда настройки
   подтянутся сами.
2. Если создаёте руками:
   - Build Command: `pip install -r requirements.txt`
   - Start Command: `python app.py`
   - Instance: **Free**
3. Environment:
   - `TELEGRAM_BOT_TOKEN` — токен бота
   - `GITHUB_TOKEN` — classic PAT из шага 1
   - `GITHUB_REPO` — `3vgenius/product-background-bot`
   - `ALLOWED_USER_IDS` — числовые Telegram ID через запятую (узнать: [@userinfobot](https://t.me/userinfobot))
   - `WEBHOOK_SECRET` — любая длинная случайная строка (Telegram принимает только латиницу, цифры, `_` и `-`; если значение содержит другие символы, бот сам заменит его на SHA-256 hex, так что сгенерированное Render значение тоже подходит)
4. После старта бот сам зарегистрирует webhook — в логах будет
   `webhook registered at https://...onrender.com/webhook`.

### 3. Keepalive

Render Free засыпает через ~15 минут простоя, а холодный старт занимает 30-60 с.
`.github/workflows/keepalive.yml` пингует сервис каждые 14 минут. Он заработает
сам, как только заполнена переменная `RENDER_URL`.

> **Ловушка на приватном репозитории.** GitHub округляет каждый запуск вверх до
> целой минуты. Пинг раз в 14 минут — это ~103 запуска в сутки ≈ **3100 минут в
> месяц**, больше всего бесплатного лимита (2000). Один такой keepalive съедает
> весь бюджет аккаунта, и обработка фото перестаёт стартовать с ошибкой «recent
> account payments have failed or your spending limit needs to be increased».
> Варианты: сделать репозиторий **публичным** (Actions бесплатны без лимита, раннер
> 4 CPU / 16 ГБ) или пинговать внешним бесплатным сервисом (UptimeRobot,
> cron-job.org) и отключить этот воркфлоу. Лимит общий на все приватные
> репозитории аккаунта — keepalive в соседнем проекте считается тоже.

> GitHub отключает scheduled-воркфлоу после 60 дней без активности в репозитории.
> Если бот перестал отвечать — загляните в Actions → Keep Render warm.

### 4. Если что-то не работает

Первый источник правды — Render → сервис → **Logs**, поле поиска над логами.

| Симптом | Что искать в логах | Причина и лечение |
|---|---|---|
| Бот молчит на `/start` | `setWebhook attempt 1 failed: HTTP 401` | Токен в `TELEGRAM_BOT_TOKEN` неверный или отозван через `/revoke`. Взять актуальный в @BotFather → API Token, вставить в Environment → Save. Проверить токен можно в браузере: `https://api.telegram.org/bot<токен>/getMe` → `"ok":true`. |
| Бот молчит на `/start` | `setWebhook attempt 1 failed: HTTP 400 … illegal characters` | Старая версия бота + секрет с символами вне `A-Za-z0-9_-`. Обновить код (текущая версия нормализует секрет сама) или вписать в `WEBHOOK_SECRET` 30–40 латинских букв и цифр. |
| Бот молчит на `/start` | строк `POST /webhook` нет, а `webhook registered` есть | Сервис спал, Telegram ждёт. Открыть `https://<сервис>.onrender.com/health`, дождаться `ok`, повторить команду. |
| «Доступ к боту ограничен» | `ALLOWED_USER_IDS is empty` | Вписать свой числовой ID (узнать у @userinfobot) в `ALLOWED_USER_IDS`. |
| `/bg` и `/once` «не запоминаются», бот отвечает «Не удалось сохранить данные в репозиторий» | `storage error … PUT settings.json: HTTP 401/403/404` | `GITHUB_TOKEN` в Render не classic или без прав. Нужен **Tokens (classic)** с галками `repo` и `workflow`. |
| «Не удалось запустить обработку» | `dispatch failed: … 403/404` | У `GITHUB_TOKEN` нет `workflow`, или `process.yml` ещё не в ветке `main`. |
| «Обрабатываю», а результата нет | Actions → Background replacement → красный запуск | Чаще всего не задан Secret `TELEGRAM_BOT_TOKEN` в GitHub (Settings → Secrets and variables → Actions). |

Браузерная проверка `getMe`/`getWebhookInfo` отвечает `404 Not Found`, когда адрес
набран с ошибкой (нет префикса `bot`, заглавная `Bot`, пробел, обрезанный токен) —
это не про токен. Отозванный токен даёт `401 Unauthorized`.

## Локальный запуск

```bash
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt -r requirements-worker.txt
cp .env.example .env      # заполнить BOT_TOKEN и ALLOWED_USER_IDS
python app.py             # BOT_MODE=polling — публичный URL не нужен
```

Либо через Docker Compose: `docker compose up`.

Локально, без `GITHUB_TOKEN`, бот работает с файлами в рабочей папке вместо
Contents API. Обработку можно делать тут же, не через Actions:

```bash
python worker.py --chat-id 0 --file-id TEST --background backgrounds/1.png \
                 --model isnet-general-use --size 1024 --dry-run --out result.jpg
```

## Тесты

```bash
pip install pytest
pytest tests/ -q
```

119 тестов покрывают пайплайн композиции, хранилище (включая запросы к Contents
API и повтор при конфликте), HTTP-слой webhook, allowlist, команды, callback'и и
проход `worker.py` целиком. Модель rembg в тестах подменяется заглушкой, поэтому
скачивать веса не нужно.

## Модели вырезания

Кнопка в `/settings` переключает два пресета:

| Режим | Модель | Размер весов |
|---|---|---|
| ⚡ Быстро | `isnet-general-use` | ~178 МБ |
| 💎 Качество | `birefnet-general` | ~900 МБ |

BiRefNet заметно точнее на волосах, стекле и мелком контуре, но медленнее.
Модель кэшируется в `actions/cache`, поэтому 900 МБ скачиваются один раз.

> **Важно про лицензии.** Дефолтная модель rembg теперь — `bria-rmbg`, и её веса
> требуют платного соглашения для коммерческого использования. В этом проекте
> модель всегда задаётся явно (`MODEL_FAST` / `MODEL_QUALITY`), чтобы этот
> дефолт не подхватился случайно. Лицензии остальных весов стоит проверить по их
> репозиториям, если бот используется в коммерции.

## Расходы и лимиты

- Render Free: 512 МБ / 0.1 CPU, засыпает без трафика.
- GitHub Actions: на **публичном** репозитории — бесплатно и без лимита минут.
  На приватном — 2000 минут в месяц на весь аккаунт; одна фотография — примерно
  минута раннера, но keepalive из этого репозитория сам съедает ~3100 минут
  (см. раздел Keepalive). После исчерпания лимита запуски просто не стартуют,
  а бот при этом уже ответил «принял» — результата не будет без объяснения.
- Telegram Bot API: файл не больше 20 МБ. Бот дополнительно ограничивает вход
  19 МБ; фото товара — 25 мегапикселей, фон — 12 мегапикселей (фон
  распаковывается в процессе Render, где всего 512 МБ, поэтому лимит ниже;
  хранится он всё равно сжатым до 3000 px по длинной стороне).
- Входные форматы: JPEG, PNG, WebP.

## Очистка фона от объектов

Фон часто снимают «как есть» — с вазой, прошлым товаром или проводом в кадре.
Кнопка **🧹 Убрать объекты с фона** запускает ту же GitHub Actions-джобу в режиме
`--task clean`:

1. rembg (модель из `/settings`) строит маску объектов на фоне;
2. маска расширяется на несколько пикселей и заполняется. Основной движок —
   **ShiftMap** (`cv2.xphoto.inpaint` из opencv-contrib): дыра заполняется
   настоящими фрагментами этого же фото, поэтому трава, ткань, дерево и бетон
   остаются резкими даже при дыре в полкадра (~15–60 с на CPU в зависимости от
   размера). Запасной — OpenCV Telea (быстрый, но на текстурах даёт размытое
   пятно; в подписи к результату это будет указано). Нейросеть **LaMa** (ONNX,
   `LAMA_ONNX_URL`) доступна по `INPAINT_BACKEND=lama` или `lama-auto`, но на
   раннере вживую не проверена и работает на 512×512 — на больших дырах мылит;
3. результат коммитится как `backgrounds/<id>_clean.jpg`, в `backgrounds.json`
   у фона появляются `original_path` и `cleaned_at`, `path` указывает на
   очищенную копию. Оригинал из репозитория не удаляется;
4. в чат приходит превью с кнопкой «↩️ Вернуть оригинал».

Защита от глупостей: если объектов меньше 0,4 % кадра — бот так и скажет и
ничего не тронет; если маска больше 60 % кадра (модель приняла сам фон за
объект) — откажется, чтобы не размазать картинку.

Честно про пределы: заполнение копирует то, что есть вокруг дыры. На
однородной фактуре результат неотличим; если объект закрывал что-то
структурное (край стола, стык стены и пола, узор), шов может быть заметен.
Самый надёжный фон — снятый пустым.

## Ограничения

- Результат приходит не мгновенно: запуск воркфлоу + установка зависимостей +
  инференс занимают примерно минуту.
- Тени и отражения не генерируются.
- На прозрачных и блестящих товарах возможны артефакты.
- Исходные фотографии и результаты бот не сохраняет.
- Не запускайте две копии с одним токеном: webhook-режим и polling начнут
  перехватывать апдейты друг у друга.

## Что проверено, а что нет

Проверено тестами и живым запуском: HTTP-слой webhook, allowlist, секретный
токен, разбор команд и callback'ов, хранилище (включая base64/sha/конфликты
Contents API), композиция и кодирование JPEG, полный проход `worker.py`.

**Не проверено** (нужен ваш токен и реальный прогон): регистрация webhook на
Render, фактический запуск `process.yml` и качество/скорость конкретных моделей
на ваших фотографиях. Тайминги инференса в этом README — оценки, а не замеры.
